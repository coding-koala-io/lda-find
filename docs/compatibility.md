# Coverage and implementation choices

This report records the minimum-server build, part 2 and subsequent working-tree corrections on 17 November 2026. The initial build used the five supplied specifications and this repository. Round 2 additionally used operator-authorized private client analysis, installed-SDK experiments and site error stacks. Endpoint labels below refer to the endpoint specification's identifiers; private specifications, vendor code and captures are not included here.

## Round-8 proxy and review corrections

This round used only the original specifications, the supplied HTTP observations and the round-3 review findings. No vendor implementation, decompiled code, private capture or installed SDK was consulted or executed. `test/fix-round8.test.js` adds eight regression tests.

Comma-separated Origin values are accepted only when all trimmed entries are identical and that origin is an allowed HTTP(S) loopback origin. Different ports, schemes or host spellings in one list, empty entries and external origins are rejected with 403. Repeated raw Origin header lines are covered too.

The CMS proxy's `application/x-www-form-urlencoded` and `text/plain` labels, including charset parameters, are accepted on POST search/count (global, index and type scopes), single-document routes and POST multi-get. The body must parse as exactly one JSON value and satisfy the route's normal shape checks. Empty bodies, actual form data, malformed JSON, multiple values and trailing data return 400. No form decoding is performed. Bulk, multi-search and Statistics content-type rules remain JSON/NDJSON.

Search charges one 16 MiB construction budget across response envelopes, hit metadata, source/explicit/partial/crop fields, highlights and facets. Aliases, copies and repeated hits count separately; overwritten selections still consume capacity. Each projection fragment is checked before retention and further projections stop on overflow. JSON byte accounting walks values incrementally, and highlight replacement charges text/tag pieces before expansion. Multi-search shares the same budget across its components. Overflow returns a short JSON 413. Conservative punctuation and duration reservations can reject a response just below 16 MiB of final JSON.

The reviewer's 444-byte amplification case is reproduced with 17 aliases selecting a synthetic 1 MiB document and receives 413; the review supplied no literal request body, so the fixture reconstructs its shape and pads valid JSON with whitespace to the stated byte count. A two-copy request succeeds. Tests also check interruption before a third alias and budget coverage for explicit fields, source, highlights, facets and multi-search.

Every compound `term`, `terms`, `prefix`, `wildcard` and `range` field predicate consumes the shared 1,024-unit compile budget. DSL nodes, text terms and term-list values count as well, across query, hit-filter and facet branches. The review's one term clause with 1,025 fields returns 400 before scanning both empty and populated indices; small compounds still match.

4xx/5xx request log lines add fixed short codes such as `invalid_json`, `origin_not_allowed`, `search_output_limit` and status-based fallbacks. Direct 404/501 responses and unexpected 500s are covered. Error messages, bodies, header values and query values are never included in those lines. `LICENSE.md` now includes the complete Apache License 2.0 text and its application appendix, sourced from the Apache Software Foundation.

## Round-7 admin and review corrections

The subsequent CMS 12 admin-screen report identified blocked loopback Origins, empty Overview filters, Explore's `*:*` query and scalar partial-source patterns, duplicate English from `standard`, missing clear operations, misleading URL-option errors and missing request logs. These corrections use only original specifications and observed request contracts. No vendor implementation was consulted or copied.

`test/admin-round7.test.js` covers raw HTTP for each runtime correction, with original synthetic records. Overview's full body was not supplied: the evidence identifies `filter:{}`, so the regression reconstructs type/language/site term facets from the spec and checks empty and populated indices. Empty predicate objects match all, including in filtered queries and filter facets. Explore's exact supplied body uses `query_string.query: "*:*"`, `partial_fields.partial_source: {include:"*", exclude:"*$$attachment"}`, a `$type` terms facet and size 25. Tests cover attachment omission, exact-type filtering, total counts and successive pages. Query eligibility versus hit-filter facet scope is preserved.

Origin accepts HTTP/HTTPS `localhost`, `127.0.0.1` and `[::1]` at any port. Other hosts, schemes, credential-bearing URLs and malformed origins remain 403. Binding remains `127.0.0.1` only, with local Host enforcement. Specific-language replies are unique real language codes, excluding `standard` and unknown/custom analyzer names even from old snapshots; their JSON string-array shape is unchanged.

`POST` and `DELETE /I/_clear?clear_index=true&clear_stats=false` clear only named-index documents and language metadata in Local Find's own store. Both flags are required Boolean strings. Statistics-only clearing succeeds without a transaction or persisted events. Both methods are covered because the observed clear URLs omit their method. Unimplemented endpoints and methods return short JSON 501 errors before URL-option validation. Invalid options on implemented endpoints retain 400; the existing E06 string-valued status contract is preserved.

`LOG_REQUESTS` defaults on outside production and can be disabled with `0`. Console lines contain only method, a route path with the service prefix and dynamic values removed, HTTP status, a short fixed error code for 4xx/5xx, and elapsed milliseconds. Query strings, bodies and headers are omitted, including on errors. Optional `DEBUG_SEARCH_REQUESTS` recording remains separate and default off.

Wildcards use a finite-state matcher without backtracking regexes, bounded to 1,024 UTF-16 code units and 64 wildcard operators per pattern. Excesses fail with 400 before scanning. Both DSL wildcards and text expressions cover the review's 32,768 repetitions of `a*`, plus the slow 25 repetitions with trailing `b` against 45 `a` characters. Partial-source patterns use the same bounded matcher. Multi-get caps 100 documents and 16 MiB total response JSON, counting duplicate results; a 17-fold repeat of one 1-MiB document receives 413. Language metadata is included in candidate bulk quota checks before mutation, preserving valid adjacent items under both index and store byte limits. Empty write `routing=` and `language_routing=` receive 400 before mutation.

Diagnostics have been relocated outside the repository; the clean-room gate passes with 0 findings. Publication wording and current-state regressions are in `test/publication-state.test.js`. See [release check](release-check.md) for final test/replay results and the unchanged Foundation proof hash. No running service was restarted and no CMS admin browser acceptance was rerun in this round.

## First-run correction, 17 November 2026

The operator reported that the site's own indexing job processed batches of 228 and 583 items, with two item errors, and that visitor search failed while assigning whole-number scores to a nullable double. This is operator-supplied runtime evidence; this correction did not execute the CMS or inspect vendor code, packages or private captures.

Search now writes numeric `_score` and `max_score` values with a decimal point, including zero and exponent notation. `max_score` covers matching hits after the hit filter and before paging; it is null for no matches and count-only searches. The same formatting applies to document values identified by `$$number`, including collections/projections, and terms from those numeric fields. Counts, versions and `$$long` values keep integral tokens and exact large integers. Only term/filter facets are implemented; no statistical values are returned by this profile.

The two reported indexing exceptions were unresolved in round 1. Single-write and bulk-item success replies are built exclusively from scalar identity/version metadata; document content cannot change their shape. Synthetic basket-page and display-settings documents with nested objects, empty objects, object arrays and colliding metadata-like properties pass explicit/generated single writes, bulk index/create and source reads. These tests establish the local shapes, not acceptance by the running client's deserializer. Round 2 established the site-side cause below.

Raw-response regressions are in `test/response-numbers.test.js`; indexing structure coverage is in `test/indexing-shapes.test.js`. No indexing reply shape was changed without evidence of a mismatch.

## Content-result correction, 17 November 2026

The CMS content-result selection sends `fields`, including `___types`, `ContentLink.ID$$number`, `ContentLink.ProviderName$$string` and `Language.Name$$string`. This was recorded using the target site's installed Find 16.3.0 SDK with synthetic content and a local request handler. The private client analysis establishes that the hit reader takes document data from `fields` or `_source`, and the projection mapper looks up each requested scalar by its complete literal name. Rebuilding those keys as nested objects leaves the projected identity missing. Scalars must remain scalars; type hierarchies and source collections remain arrays.

Explicit selections now return those literal keys under `hits.hits[].fields`. Source lookups support both nested objects and submitted literal dotted keys, with exact keys taking precedence. Get-by-ID field selections use the same shape. Named `partial_fields` now return separate `fields[name]` source fragments, including `_all`, rather than merging their contents together. Partial fragments retain their original nested structure.

The round-1 decimal formatting also required a CMS identity exception: `$$number` includes Int32 fields. `ContentLink.ID$$number` and `ContentLink.WorkID$$number` retain integral tokens in explicit projections and ContentLink source objects. The installed SDK rejected a decimal ID when constructing a content reference; an integral scalar ID with the corrected keys produced the expected reference and language. Scores and other existing decimal formatting remain covered separately. This exception does not infer CLR types for arbitrary application numeric fields.

`test/content-projection.test.js` constructs the recorded request shape independently and asserts raw response tokens, exact key placement, scalar/collection shape and named partial wrappers for synthetic documents. SDK replay validates the content-result selection and mapping; it does not establish full running-site search or CMS repository hydration. No running service was restarted and no proof data was mutated by this correction.

The real indexing stacks locate both basket-page and display-settings failures in `DuplicateFieldNameContentModelFilter.CheckDuplicateFieldName`, called by ContentApi conversion during outgoing Find serialization. The stack then passes through `SerializeObjectsToJsonRequest`; this is before a response can be consumed. These remain site-side serialization defects, outside this server repository. Changing acknowledgement JSON cannot repair them.

## Search correction, round 3, 17 November 2026

The target Foundation model binder reads the `search` query parameter. Requests using `q` leave the term empty: the product query has no full-text clause and the content-search method skips its query entirely. A direct local request using `search=jacket` instead reached unified search and failed because `script_fields` was unsupported. The evaluator must not invent a term absent from a request.

The installed SDK probe recorded these clause shapes using synthetic inputs:

1. Products: nested `filtered` wrappers around `query_string` with the input term and `analyzer: standard`; exact `Language.Name$$string` language filter; `___types` hierarchy term for the commerce entry base type; literal CMS identity fields.
2. Unified content: `query_string` over `SearchTitle$$string.standard`, `SearchText$$string.standard`, `SearchSummary$$string.standard` and `SearchAttachmentText$$string.standard`; a type `or` containing `ISearchContent`, `PageData` and `MediaData`; selected scalar fields, named `SearchMetaData` partial fields, and title/summary/text/attachment highlights. CMS registry expansion supplies PageData/MediaData, so no inferred interface alias is appropriate.
3. Excerpts: four native `ascropped` script fields for summary, text, attachment and attachment text, with explicit `field` and `length` parameters. The local implementation accepts only that named native projection and returns scalar strings alongside other selected fields. Cropping uses the first requested number of stored characters; hosted word boundaries, HTML handling and ellipsis are unverified. It executes no script text.

The preserved 810-document store includes 228 pages. Direct replay of the SDK product shape returned six hits for `jacket` (no boots), eight for `shoes` and zero for `zzqxnothing`. The unified SDK shape returned six for `jacket`, zero for nonsense and 29 for a title word; the expected titled page was present. Adding an explicit English filter returned 28 of the title-word hits; Swedish and nonexistent language filters returned zero. The installed SDK consumed all six jacket page results with titles and excerpts. The proof store's hash did not change.

These SDK captures reproduce the relevant text/type/projection contracts, not the site's complete runtime visitor, market, site, best-bet or cache composition. Existing synthetic tests cover grouped publication, access, language, type and numeric boost predicates. No full-text or type predicate was relaxed. The running service requires an operator restart before live-site acceptance. Optional `DEBUG_SEARCH_REQUESTS=1` records search bodies only under the configured data folder, with credential-named properties redacted and a 10 MiB cap; it defaults off. Raw SDK captures and the replay report remain in ignored local data. Tracked regressions use original synthetic values.

## Numeric projection correction, round 4, 17 November 2026

The real `?search=jacket` request reached product and content search after round 3, then failed while projecting `PageLink.ID$$number`: the client attempted to cast `System.Double` to `System.Int64`. The root cause was round 1's response serializer treating every `$$number` field as a double. The round-2 ContentLink exception covered only that reference name and left PageLink and arbitrary integral application fields exposed.

The suffix-wide conversion and reference-name exception are removed. Document values retain their indexed numeric token types. The parser records decimal/exponent tokens as weak metadata on their containing objects; cloning, scalar/array field selection, partial fragments, persistence and restart preserve that metadata. Integral tokens, including exact Int64 values, remain integral regardless of field name. Whole-valued indexed decimals retain their decimal syntax. Computed `_score` and `max_score` values remain explicitly decimal at their origin. Numeric facet terms follow their indexed token types. Existing persisted tokens are authoritative; CLR types are not inferred from names, and decimal syntax already discarded by older persistence cannot be reconstructed from an integer alone.

Raw-response regressions place PageLink.ID, ContentLink.ID, arbitrary counts, an Int64, fractional decimals and whole-valued decimals in the same hit, including search, multi-search, source reads, explicit projections and partial fields. A disk restart regression verifies that numeric types survive saving and reloading. `npm test` passed all 65 tests.

An original probe using the site's installed Find 16.3.0 SDK recorded product/content requests and consumed responses generated through the corrected HTTP server from a memory-only snapshot of the existing proof store. The SDK mapped six jacket product references with English language and six unified content results with titles/excerpts; nonsense requests returned zero. A PageData selection mapped both PageLink.ID and ContentLink.ID in ten real page hits. A separate synthetic SDK hit mapped both IDs, an integral count, fractional/whole CLR doubles and a CLR decimal together. The 810-document proof store's SHA-256 remained unchanged. Captures, responses and the report stay in ignored local folders; tracked fixtures use synthetic values.

This validates the recorded SDK request shapes and mapping, not the site's full visitor/market/site composition or CMS repository hydration. No running service was restarted. Local Find must be restarted to load this correction before live-site acceptance.

## Visitor Statistics correction, round 5, 17 November 2026

The operator verified real-word visitor searches after round 4, but a zero-hit query reached the Statistics client's did-you-mean command and failed on HTTP 501. The authorized private client contracts require a Statistics envelope with string `status` and an array `hits`, rather than the document search envelope. GET `/{index}/_didyoumean?query=...`, `/_spellcheck?query=...` and `/_autocomplete?prefix=...` now return exactly `{"status":"ok","hits":[]}`. Optional size, cutoff and tag parameters are accepted without producing suggestions.

POST `/{index}/_track/` and `/{index}/_track/{id}` accept the SDK's query tracking JSON (`q`, `query.hits`, `query.took`, optional `query.results`, plus optional metadata). Replies contain `status:"ok"`, `track_id:"local-noop"`, and all-zero UUID strings for `track_uuid` and `track_sid`. GET `/{index}/_track` accepts hit tracking options and replies with `status:"ok"` and `track_id:"local-noop"`. These fixed placeholders identify no visitor and correlate no events. Nothing is retained in memory, saved to disk, logged or forwarded. Search diagnostics explicitly exclude tracking paths, including tracking IDs named `_search` or `_msearch`.

All routes retain the HTTP service's full-prefix, loopback, origin, body-limit and JSON content-type checks. Each requires one concrete index; `_all`, reserved names, wildcards and multi-index selections are rejected. A missing index receives the same empty/no-op reply without creating an index. Unsupported Statistics routes and methods retain explicit errors. `stats:false` remains truthful: there is no statistics collection, suggestion engine or analytics dashboard.

Eight original synthetic tests in `test/statistics.test.js` check raw reply text for every operation, both POST ID forms, hit tracking, optional metadata, prefix/index/method boundaries, malformed input, unchanged disk/memory state and absent request recordings even with diagnostics enabled. An original probe using the site's installed Find and Statistics 16.3.0 assemblies made six actual loopback requests and successfully parsed `GetDidYouMean`, `GetSpellcheck`, `GetAutocomplete`, two `TrackQuery` POST replies and one `TrackHit` GET reply. Its transport blocked requests outside the temporary local endpoint. The proof store's SHA-256 was unchanged. Probe artifacts remain ignored; no running service was restarted.

The retained visitor-search source calls did-you-mean on zero results, autocomplete through the CMS public proxy, and query tracking through `.Track()`. No additional unanswered Statistics operation was found in that source. This is a bounded source review and installed-SDK replay, not live browser acceptance. Totals (`/_stats/totals`), GDPR and sanitizer management remain unsupported; enabling features that call them needs further work.

Validation passed all 73 tests (65 existing plus eight Statistics regressions), with zero failures or skips. The default `npm test` launcher exited before producing runner output in this session; `npm --script-shell=powershell.exe test` successfully ran the unchanged test script. Direct `node --test test/*.test.js` also passed all 73 tests.

## Supported evaluator scope

The evaluator handles `query_string`, field text queries, match-all, constant-score, filtered, term/terms, prefix/wildcard, IDs, exists/missing, and/or/not/bool, query/fquery wrappers and basic nested isolation. Numeric `function_score`, `custom_filters_score` and `dis_max` compose local scores. All scoring is approximate. Wildcards operate on tokens in text queries and whole values in wildcard predicates.

Not implemented: fuzzy queries/options, child relations, more-like-this, boosting queries, custom/script scoring, native auto-boost/decay/hit-count presets, script filters and script fields other than native `ascropped`, geo predicates, histogram/date/range/statistical/geo/nested facets, all-terms facet expansion, nested/geo sorting and external attachment extraction. Unsupported query members are rejected even on an empty index. Broad text grammar is limited to words, phrases, parentheses, field selection, AND/OR/NOT and wildcards; it is not a complete query-string parser.

## Operational limits and acceptance still required

Requests have a 16 MiB body limit, framed requests at most 20,000 records, headers a 15-second timeout and complete requests a 30-second timeout. The evaluator scans the in-memory corpus on one JavaScript thread. Stores enforce 10,000 documents / 64 MiB per index, 25,000 documents / 128 MiB aggregate, and 128 indices; UTF-8 records, identities and settings count toward byte quotas. Exceeding capacity returns 413, including per-item bulk failures, with rollback on a failed save. Existing oversized stores fail startup. Persistence streams a bounded atomic snapshot, caching unchanged document serialization and saving once per bulk transaction; disk copying remains proportional to the bounded snapshot. Text parsing shares DSL nesting (40) and node/term/field-predicate (1,024) guards shared across query, hit-filter and facet branches and rejects expressions over 64 KiB with 400. Search URL size/from paging is validated and applied; unknown, duplicate, empty or invalid options are refused, including scroll (501). Use small development corpora; these are local resource limits. A failed disk save returns HTTP 500; this build does not inject 429 responses or reproduce client retry scheduling.

Before claiming CMS compatibility, run the target CMS 12 version through startup/settings, multilingual publish/edit/delete, full reindex including external-best-bet behavior, real visitor/UI queries, repository hydration and fault recovery. Runtime evidence is also needed for settings language conversion, actual analyzer names, enabled extensions, reserved/non-ASCII URL behavior, caching and queue policies. Tests of this service alone cannot close those gaps.

The original two parts added no admin UI, request capture, Windows service management, release packaging or public publishing. Later corrections added the opt-in local search diagnostics and visitor Statistics no-ops described above; other rank 5 extensions remain outside the profile. No runtime dependency, telemetry or external service call was added; IPv4 loopback remains mandatory. Documentation and tests contain synthetic keys only. No commits were made.
